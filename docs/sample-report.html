Critical

Exposed application secrets to backing data store on 192.168.56.103

The exposed file typically contains the credentials the application uses for its own database, and that database is reachable on this host. Retrieving the file and connecting is two steps with no exploitation required — this is a configuration error that yields the data directly.

Outcome Direct authenticated access to the application's database
Confidence confirmed
  1. Application secrets exposed over HTTP — Environment file exposed
  2. Database service reachable on the same host — MySQL 5.7 detected
RemediationBlock external access to dotfiles and version-control metadata at the web server, rotate every credential that was exposed, and restrict the database to application hosts only.
Critical

Unauthenticated SYSTEM via MS17-010 on 192.168.56.102

MS17-010 grants SYSTEM on the target with no credentials and no user interaction. On a domain-joined host this is usually the shortest path from network access to domain compromise, since SYSTEM can read cached credentials and machine account secrets.

Outcome SYSTEM-level code execution without credentials
Confidence confirmed
  1. MS17-010 present — MS17-010 SMB remote code execution
RemediationApply MS17-010. If the host cannot be patched, disable SMBv1 and isolate it at the network layer.
https://attack.mitre.org/techniques/T1210/
Critical

Unauthenticated Redis to remote code execution on 192.168.56.104

An unauthenticated Redis instance accepts CONFIG SET, which lets an attacker relocate the dump file and write arbitrary content to disk — commonly an SSH authorized_keys entry or a cron job. This converts read access to the keyspace into code execution as whatever account Redis runs under.

Outcome Command execution as the Redis service account
Confidence confirmed
  1. Redis reachable without authentication — Redis exposed without authentication
RemediationSet requirepass, bind Redis to localhost or a trusted interface, and enable protected-mode. Rename or disable CONFIG in production.
Critical

Anonymous write access to a file share on 192.168.56.101

A writable anonymous share allows content to be placed on the host. Where the share backs a web root, a scripts directory, or a startup path, that becomes execution. Even where it does not, it enables planting lures for credential capture.

Outcome Arbitrary file placement, and code execution where shares are executed
Confidence confirmed
  1. Writable share without authentication — SMB shares accessible without authentication
RemediationRemove anonymous access and require authentication on every share. Audit the filesystem paths the writable shares expose.
High

NTLM relay to authenticated SMB access on 192.168.56.101

With SMB signing unenforced, an authentication attempt captured via name-resolution poisoning can be relayed to this host instead of being cracked offline. The relay inherits the victim's privileges, so a single mistyped hostname on the network becomes authenticated access here.

Outcome Authenticated access to file shares, and often code execution
Confidence confirmed
  1. SMB signing not enforced — SMB signing not required
  2. Name-resolution poisoning surface present — SMB shares accessible without authentication
RemediationEnforce SMB signing on all hosts, and disable LLMNR and NBT-NS via Group Policy so there is nothing to poison.
https://attack.mitre.org/techniques/T1557/001/
High

SNMP disclosure to device credentials on 192.168.56.105

A default community string exposes the full device MIB. On network equipment this routinely includes the running configuration, which carries local account hashes, SNMP write communities, and shared keys reused across the estate.

Outcome Device configuration, and frequently credentials in cleartext
Confidence confirmed
  1. SNMP readable with a default community — SNMP readable with default community 'public'
RemediationReplace default community strings, restrict SNMP by source address, and migrate to SNMPv3 with authentication and privacy.
High

World-readable NFS export to credential material on 192.168.56.106

Unrestricted exports commonly contain home directories, which carry SSH private keys and shell history. With no_root_squash they also allow writing an authorized_keys file directly.

Outcome Access to home directories, SSH keys and backups
Confidence confirmed
  1. NFS exports readable without restriction — NFS exports world-readable
RemediationRestrict exports to specific hosts, enable root_squash, and avoid exporting home directories where possible.
High

Cleartext protocol to credential capture and reuse on 192.168.56.101

Credentials sent over these protocols are recoverable by anyone positioned on the path. Because administrators reuse credentials across systems, a single capture typically unlocks more than the service it was taken from.

Outcome Captured credentials, usable wherever they are reused
Confidence firm
  1. Credentials traverse the network in cleartext — Telnet exposed without transport encryption
  2. A second host accepts the same credentials in principle — vsftpd 2.3.4 backdoor command execution
RemediationRetire cleartext protocols in favour of SSH, SFTP and TLS-wrapped equivalents, and rotate any credential that has traversed them.
